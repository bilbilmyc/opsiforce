# App Details are per-environment; each ProjectEnvironment is its own App

Status: accepted — implemented (migration `0047_project-app-per-environment.sql`; `project_app` is keyed by `project_environment_id`)

App Details (name and description) were stored once per Project in `projectApps`, keyed by `projectId`, while the source of those details — `app.meta.json` — has always been **per-environment** (each ProjectEnvironment carries its own copy). That mismatch is the cross-environment clobber: every environment's 30s `live` heartbeat wrote the one shared row, so a published environment running an older snapshot kept overwriting Development's curated name (PR-1682, review comment #3). **We resolve it by moving `projectApps` to be keyed per ProjectEnvironment** — each environment is now its own App with its own App Details — so the DB matches the file reality and each environment writes only its own row. The Project becomes a shell that groups several Apps; a **Pin** still designates at most one of them to represent the Project in Makara.

This is the deliberate reverse of the prior glossary, which read "one Project produces one App" and "the name/description Makara shows are project-level (one App), not per-environment." Those entries (App, App Details, Pin, Go-live, Project) are rewritten in `CONTEXT.md` to match.

## Considered options

- **Keep App project-level; gate identity writes to Development only** (the handoff's recommendation for comment #3). The backend would `upsertProjectApp` only when the gateway key's `key === projectId` (Development, per [ADR-0002](0002-development-environment-reuses-project-id.md)) and skip published environments. Fixes the clobber, requires no migration — but leaves the DB row permanently out of step with the per-environment files, cannot show a published App's own identity (the truth of what that URL serves), and carries source-gating logic in the hot path. Rejected: it treats the symptom; the row being project-level *is* the mismatch.
- **Per-environment App** — chosen. The clobber disappears structurally (no gating needed), the pinned App's Makara entry is exactly what that environment runs, and identity can be curated independently per environment.

## Consequences

- **Schema.** Primary key moves from `project_id` to `project_environment_id`; `project_id` is retained (denormalized) for grouping and the pin constraint; the `pinned_environment_id` and unused `icon_url` columns are dropped (the row *is* the environment now; `icon_url` had no reader or value-writer — an App's real icon is its per-environment `favicon.svg` file); `is_pinned` lives on each environment's row; a partial unique index `(project_id) WHERE is_pinned` re-enforces "at most one pin per Project" — an invariant the single-row design enforced structurally and the multi-row design must assert.
- **Makara.** `internal/apps.controller.ts` drops the `coalesce(pinned_environment_id, project_id)` join and reads the pinned environment's own row; the catalog name/description become that App's own, not a shared project identity.
- **Editing** targets the **active** environment's App: `updateApp` takes an `environmentId`, writes that environment's `app.meta.json` (each ProjectEnvironment has its own `directory`) and its own row. A published App's edits are transient — recopied from Development on its next publish — consistent with the existing "Publish transports source" rule.
- **Pinned-environment deletion** now clears the pin via FK cascade on the App row, instead of silently repointing the public pin to Development through the old `coalesce`-to-`project_id` path. This is a behavior improvement, not just a refactor.
- **Heartbeat churn.** The 30s `live` keep-alive would otherwise write one row + fire one SSE per *live environment* every beat. An on-change guard in `upsertProjectApp` reads the environment's stored row first and skips both the write and the SSE when the reported name/description are unchanged, so steady heartbeats are no-ops; only a first go-live (row insert) or a real rename writes and notifies. Readiness (`markLive`) still refreshes every beat, since it is rebuilt from pushes after a backend restart.
- **Backfill.** For each existing project-level row, Development's row (`project_environment.id = project_id`) inherits the existing name and description, and every other environment that has been published (`deployed_commit_sha IS NOT NULL` — the same signal the UI uses for "an app runs here", independent of transient status) is seeded a row from the same (Development-authored) values; the pin — with original `pinned_at`/`pinned_by_id` — is set on `coalesce(old pinned_environment_id, project_id)` and cleared elsewhere, so it is preserved exactly. Migrations cannot read the filesystem, so published environments are seeded from the only DB-available source and re-assert their true values on their next heartbeat.
