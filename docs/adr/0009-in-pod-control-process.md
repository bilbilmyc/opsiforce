# App restarts are triggered through an in-pod control process, not exec or file-watching

Status: accepted

Editing a `ProjectEnvironment`'s Environment Variables only matters once the App re-reads `opsiforce.env.json`, and the app template reads it exactly once, at process boot. The only restart the platform had was pod recreation (`ProjectService.restart` deletes the pod), which is far too blunt for "I changed an API key": it tears down the agent session servers, code-server, and Datasette along with the app, and takes the pod-schedule + image-pull + workspace-boot path instead of the ~2s an app process restart costs. Something *inside* the pod has to deliver the lighter restart, because from outside a pod there are only two channels: an HTTP port or the Kubernetes exec API.

**A fifth guarded process.** The agent container already runs four `guard`-supervised processes side by side (`entrypoint.sh`): the app (`startup.sh`, which itself wraps `app-backend`/`app-frontend` in inner guards), `opencode serve`, `code-server`, and `datasette`. We add a fifth: a minimal HTTP control server (a small Go binary baked into the image like the existing `agent-log-writer`) listening on its own port on the pod IP. The backend reaches it exactly the way it already reaches OpenCode on `:4096` — direct pod-IP HTTP inside the cluster, no ingress route. Auth is a per-pod random token generated by the backend at pod creation and injected as an env var; every control call carries it in a header (the same trust pattern as the runtime proxy's `x-proxy-control-token`).

Its first route is `POST /restart-app`: kill the app process groups, and the inner guards revive them with the new env values a couple of seconds later. Apply-with-restart in the Environment Variables editor is therefore: atomic file write on the shared mount, then one POST. The channel is deliberately generic — future needs (clear cache, rerun migrations, process status) ride the same port instead of inventing new signaling.

**Why not the obvious alternatives.** The natural-looking "watch the env file with inotify" does not work here: inotify only reports writes made through the same mount on the same node, and the backend writes through *its own* CephFS client. Events do not propagate across CephFS clients, so an in-pod watch fires for agent edits but never for backend edits — and deceptively *does* work on single-node hostPath dev setups, which is exactly the kind of silent prod-only breakage we refuse to ship. Kubernetes `pods/exec` avoids the image change entirely, but grants the backend service account exec rights over every agent pod — a material expansion of blast radius at the same time as the agent-pod network-policy hardening (#1480) is trying to shrink it.

## Considered options

- **Kubernetes `pods/exec`** — backend runs `pkill` in the pod via the API-server websocket. No agent-image change, works for already-running pods immediately. Rejected: `pods/exec` RBAC makes the backend omnipotent inside every agent pod, against the direction of #1480.
- **inotify on `opsiforce.env.json`** — fully automatic apply, no backend orchestration. Rejected: inotify events do not cross CephFS client mounts, so backend writes are invisible; works locally, breaks in prod.
- **Sentinel file + polling loop** — backend drops a marker on the shared mount, an in-pod loop `stat`s it every ~1s. Works everywhere with trivial code. Rejected: it is polling with up-to-a-second latency and a marker-file protocol to maintain, when an evented channel costs barely more.
- **Keep pod recreation** — zero new code. Rejected: disproportionate disruption for a config edit, and on Development it recycles the agent pod the user is actively working in.

## Consequences

- Agent image change ⇒ `agent-image-version.json` bump and the usual rollout; pods still on an older image have no control port, so the apply path falls back to full pod recreation until they are refreshed.
- The control token becomes part of the pod contract: generated at pod creation, known to the backend, never exposed through ingress. Token rotation = pod recreation.
- One more port on the agent pod that #1480's network policies must explicitly scope to backend-only access.
- `startup.sh`'s inner `guard app-backend` / `guard app-frontend` wrappers are now a load-bearing interface: the control process restarts the app *by killing it*, relying on guard's revive. Renaming or unwrapping those processes breaks the restart path.
