# App liveness is pushed from the pod over the gateway channel, not polled

Status: accepted — implemented 2026-06-16

The platform needs to know two things about a Project's App at runtime: that it has **gone live** (the agent wrote `app.meta.json`, giving the App an identity) and that its process is **serving** on its port. Both gate user-visible behaviour — the in-workspace app pane appears at go-live, and publish/duplicate/schedule all wait for the App to serve. Until now every one of these was answered by polling: a detection loop in `AppService` hit `http://{podIp}:3000/api/app-meta` every 3 s while a client watched the status stream, and three further loops (publish, duplicate, schedule) independently asked "is the app serving yet?". The detection loop overlapped its own requests (3 s interval, 5 s timeout), reset its failure budget on every SSE reconnect, could not tell "no app yet" from "pod unreachable", and logged its failures at debug — so when an environment's pod was assigned an IP but never became reachable, the backend made ~141 doomed fetches against it, silently, correlating with a multi-GiB memory spike.

**The pod now tells the backend, instead of the backend asking.** The in-pod `agent-control` process (already present for `POST /restart-app`) watches `app.meta.json` via inotify and probes the app's local port, and **pushes** an idempotent `{serving, live, name, description}` state to the backend over the **existing Service Gateway channel** — the same per-environment bearer token (`SERVICE_GATEWAY_API_KEY` → `{projectId, environmentId, tenantId}`) that agents already use to register schedules. A single `AppReadinessService` owns per-environment app state and is the one thing the preview gate, publish, duplicate, and schedule consume (`awaitReady`). The four poll loops are deleted.

Pushing is the right direction because the producer — the pod — is the only party that knows the exact moment go-live happens, and the obvious passive alternative (let the runtime proxy report it from real traffic) cannot bootstrap the common case: a freshly-built Development App has no traffic to observe until its pane is shown, and the pane is gated on the very signal we are trying to produce.

## Considered options

- **Harden the backend poll** — keep a backend→pod probe but make it single-in-flight, backed off, bounded, and surfaced. Fixes the memory bug but still polls an endpoint that is silent for most of an App's pre-go-live life, and still probes pod-IP from outside. Rejected as the primary mechanism.
- **Proxy real-path sensing** — have `opsiforce-proxy` report the App up/down from the traffic it already carries. Kept for the **down** direction (its existing failure report is a real-path health signal) but rejected as the detection mechanism: the proxy is request-driven and cannot observe a no-traffic Development App, so it cannot bootstrap go-live.
- **In-pod push over the gateway** — chosen. The egress already exists, is authenticated, is used today by agents (schedules), and is in the allow-list of the planned `#1480` network policy, so it adds no new network path.
- **A backward-compatible fallback for old pods** — keep a bounded verify for pods whose image predates the push. Rejected: the platform currently runs only Development environments at low volume, so we instead bump the agent image and recreate every pod onto it rather than carry a dual code path.

## Consequences

- Four independent poll loops collapse into one `AppReadinessService`. `app.meta.json`-derived identity continues to persist in `projectApps`; the live/serving state is ephemeral (runtime-only, like pod readiness) and is rebuilt from pushes.
- Reliability rests on the push, not a probe: pushes are **at-least-once** (agent-control retries until the backend acks; the backend is idempotent), and agent-control **re-stats the file and re-probes on startup** so a go-live that happened while it was down is not missed. Because identity is persisted, a backend restart does not lose detection.
- With no probe, a pod that is reachable by its kubelet but **not reachable cross-pod** (a CNI fault) cannot push out, so its go-live is never detected — silently, with no error surfaced. This is accepted: such a pod also fails the backend's `:4096` calls, so the agent chat breaks visibly, and at-least-once delivery means detection self-heals once the network recovers.
- `agent-control` is a binary baked into the agent image, so this ships only when pods are **recreated onto a new image**. An `agent-update` migration cannot *carry* the binary (it patches volume files, not the image), but it is still the rollout lever: an empty migration that sets `requiresPodRecreate: true` makes the boot-time project sweep recreate every pod onto the current image — the same pattern used to roll out the log-writer binary (`20260526_update_log_writer`). A plain image-version bump alone only triggers an in-place opencode reload (`requiresOpenCodeReload`), which does not swap a baked binary.
- The gateway token equals a fixed environment identity, so a pod cannot report state for another project. Because the token lives in the pod's environment, App code could report its *own* state — a cosmetic, self-only effect already inside the gateway token's trust boundary.
